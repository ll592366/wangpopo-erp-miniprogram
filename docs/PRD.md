## 1. 产品目标

1. 让**门店**与**总仓**之间的食材流转可记录、可追溯、可对账 —— 门店按需申请、管理端按量确认，杜绝"要了多少、给了多少、用了多少"三本账。
2. 菜品按**内嵌消耗食材清单**自动换算扣减本店食材，门店不用心算，误差降到 0。
3. 让**管理端**在一处掌握总仓库存、食材预警与各分店经营（卖出份数 + 消耗用量）。
4. **MVP 目标**：**1 个预置管理端 + 3 家分店**，单食材单菜品跑通"采购 → 门店申请 → 管理端确认 → 出品消耗 → 剩余实点"完整闭环（**只记数量，不记金额**）。

## 6. 关键业务规则

### 6.1 库存流转（以某分店 · 牛肉为例）

```
[总仓]                             [分店·牛肉]
采购 50 斤（0 → 50 斤）
    │
分店提交食材申请「牛肉 3 斤」 ──>   申请单 pending（库存不变）
    │
管理端确认（同一个事务）
    ├─ 总仓 50 → 47 斤
    └─ 分店  0 →  3 斤              正式库存 3 斤
    │
卖出 3 份牛肉火锅（每份 0.5 斤）
    ↓
库存 −1.5（当前 1.5 斤）
    │
剩余实点 1.5 斤
    ↓
差异 = 0，无预警
    │
次日结转
    ↓
次日期初 = 1.5 斤
```

### 6.2 核心公式

| 场景 | 公式 | 案例 |
|------|------|------|
| 出品扣减 | `扣减量 = 份数 × 每份用量` | 牛肉火锅 每份 0.5 斤 × 3 份 = 1.5 斤 |
| 差异 | `差异 = 实际剩余 − (期初 + 入 − 出 − 耗)` | 1.5 − 1.5 = 0 |
| 申请确认 | `总仓 −申请量` 且 `门店 +申请量`（**同一事务，一次性结清**） | 申请 3 斤 → 总仓 50→47 / 分店 0→3 |

### 6.3 状态字段（数据模型提示）

- 食材申请单：`pending`（待处理）/ `confirmed`（已确认）/ `rejected`（已驳回）/ `cancelled`（已撤回）
- 食材库存：仅「正式库存」一种口径
- 出品记录：`confirmed`（已扣减）/ `reversed`（已撤回）
- 差异记录：`none` / `short`（实际<账面）/ `over`（实际>账面）

### 6.4 业务约束

1. **门店账号与门店强绑定**：一个门店端账号只能操作本店数据（1 账号 = 1 门店）；越权 → `1003 STORE_OUT_OF_SCOPE`。
2. **分店编码规则沿用**：门店端注册时按店名自动生成编码（含字母数字取之，纯中文用 `S01 / S02 …` 顺序编号），编码仅用于展示与编号，不参与业务判定。
3. **首日期初 = 0**：门店首日期初为 0，通过管理端确认申请 / 采购入库产生库存。
4. **负库存拦截**：库存不足时禁止扣减；**申请确认时总仓不足同样拦截**，提示"库存不足：X 当前仅 N 斤，需要 M 斤"（错误码 **2001**）。
5. **申请校验**：申请数量必须为正数（**2002**）；仅**本店门店端**可发起（越权 → **1003** `STORE_OUT_OF_SCOPE`）；仅**管理端**可确认 / 驳回（其它角色 → **1003** `NO_ROLE`）；驳回原因必填。
6. **并发安全**：同一食材并发扣减 / 并发确认使用事务或乐观锁，避免超扣，且**同一申请单不可被重复确认**。
7. **管理端不可新增**：创建第二个管理端一律 `1003`。

### 6.5 食材申请单状态机（沿用 v0.6，不变）

```
pending ──(管理端确认·一步到位)──> confirmed（终态；总仓 −申请量 / 门店 +申请量，同一事务）
   │
   ├────(管理端驳回·必填原因)────> rejected（终态；库存不变）
   │
   └────(门店撤回·仅本人 pending)→ cancelled（终态；保留单据、非物理删除，库存不变）
                                     ▲
        门店「复制为新单」→ 新 _id / status=pending 重新提交
        （rejected 与 cancelled 两种终态均可「复制为新单」，原单保留）
```

| 状态 | 中文 | 可执行动作 | 库存影响 |
|------|------|-----------|---------|
| `pending` | 待处理 | 管理端：确认 / 驳回；门店：撤回 | 无 |
| `confirmed` | 已确认 | 无（终态） | 总仓 −申请量；门店 +申请量（同一事务） |
| `rejected` | 已驳回 | 无（终态）；可**复制为新单**重提 | 无 |
| `cancelled` | 已撤回 | 无（终态）；可**复制为新单**重提；管理端待处理列表不显示 | 无 |

**撤回规则**：门店可撤回**自己**的 `pending` 申请 → `status='cancelled'`；**终态、保留单据、非物理删除**，并写 `op_log`（`requisition.cancel`）；撤回不产生任何库存影响。管理端「待处理申请」列表**只查 `pending`**，`cancelled` 不出现在待办中。

**重提口径（新单据方案）**：`rejected` 与 `cancelled` **两种终态**均在「申请记录」中提供「**复制为新单**」——生成一张**全新申请单**（新 `_id`、状态回到 `pending`）后再次提交，**原单保留不变**。

**单据留痕字段**（`requisition` 集合，须全部落库 + 写 `op_log`）：申请人 `applicantId`、申请时间 `createdAt`、门店 `storeId`、明细 `items[{itemId, qty}]`、状态 `status`、处理人 `handledBy`（确认人 / 驳回人同字段）、处理时间 `handledAt`、驳回原因 `rejectReason`；`op_log` 的 `action` 分别记 `requisition.create` / `requisition.confirm` / `requisition.reject` / `requisition.cancel`。

### 6.6 数据字段定义（食材 / 菜品）

**食材 `material`**

| 字段 | 必填 | 规则 |
|---|---|---|
| 名称 `name` | ✅ | **全局唯一**（重名 → `3002`） |
| 单位 `unit` | ✅ | **自由输入文本**（如 斤 / 个 / 份 / 包 / 瓶）；**不做固定枚举、不做单位换算** |
| 低库存预警值 `lowStockThreshold` | ⭕ 选填 | 数字；为空则取全局默认值（2） |
| 是否启用 `isActive` | — | 停用 = 软删除 |

**菜品 `dish`**

| 字段 | 必填 | 规则 |
|---|---|---|
| 名称 `name` | ✅ | **全局唯一**（重名 → `3002`） |
| 消耗食材清单 `consumeItems` | ⭕ 可为空 | 数组，**可为空**；每行 = `{ materialId, qty, unit }` + 可选 `portions`（**v0.9 多维字段**） |
| 是否启用 `isActive` | — | 停用 = 软删除 |

> **菜品的「消耗食材清单」即原「配方」数据，内嵌在菜品里，不再单独建模块。**
> **字段定义（v0.9 修订，原样存、不换算）**：
> - **基本维度**：`{ materialId, qty, unit }` —— `qty` 与 `unit` **原样存**，对应老板原话「食材 数量 单位」写法（如「腰花 2 包」「凤爪 1.7 斤」「扁豆 400 克」「梅菜扣肉末 4 勺」）；不做任何单位换算 —— 老板表里没给「1 包等于多少斤」就不强算。
> - **份数维度（可选）**：`{ ... portions: N }` —— 仅用于老板原话带「= N 份」/「做 N 份」的款式（如「鱿鱼耳丝 3 包 2 份」→ `qty=3, unit='包', portions=2`；「肥肠 1 大包 3 份」→ `qty=1, unit='大包', portions=3`）；缺省 = 该行 qty 即**单份用量**。
> - **扣减公式（v0.9 修订）**：`production.create` 按菜品内嵌清单**逐项**扣减 —— 当行无 `portions` 时扣 `qty × 份数`；当行有 `portions` 时扣 `qty × 份数 / portions`（即 **每份实际消耗** = `qty / portions`），单位沿用食材自身 `unit`，**0 单位换算**。公式表见 §6.2。

### 6.9 门店启停规则（v0.8 新增）

1. **「闭店」= 停用、可复业**：不是永久关闭，**不删除任何数据**；门店可随时「复业」恢复营业。
2. **闭店影响登录（已定）**：门店闭店后，该门店的**门店端账号登录一律被拒**；错误码**复用 `1001`**，message 与「密码错误」**区分**（明确提示"该门店已闭店，如需恢复请联系管理端"）。
3. **闭店影响已登录会话与写动作（已定）**：闭店前**已登录的会话一并失效** —— 不能靠"登不进去"兜底；**闭店期间门店端一切写动作（申请发起 / 撤回 / 出品 / 实点等）均被拒**，**已登录态的请求同样拒绝**，不可"登录态仍可写"。
4. **闭店影响统计展示**：门店闭店后，管理端「分店经营」**仍然列出这家店**，并加「**已闭店**」标记；其统计区间**截止到最后一次营业日**，不显示之后的空数据。
5. **数据字段**：`store` 集合新增 `status`（`open` / `closed`，默认 `open`）与 `closedAt`（闭店时间）；**复业时清空 `closedAt`** 并把 `status` 置回 `open`。
6. **权限**：仅管理端可执行 `store.toggle`（闭店 / 复业）；门店端不可自停用。

## 附录 · 数据模型（给架构师参考，非需求）

```text
# 食材 material
{ _id, name,            // 全局唯一
  unit,                 // 自由输入文本（斤/个/份/包/瓶…），不换算
  lowStockThreshold?,   // 选填数字，为空取全局默认 2
  isActive, createdAt }

# 菜品 dish（消耗食材清单内嵌，无独立配方集合）
{ _id, name,            // 全局唯一
  consumeItems: [{ itemId, qty }],   // 每行 = 食材 + 每份用量，可为空
  isActive, createdAt }

# 采购入库 purchase（无金额、无供应商）
{ _id, itemId, qty, operatorId, createdAt }

# 食材申请 requisition（状态机）
{ _id, storeId, applicantId,
  items: [{ itemId, qty }],
  status: pending | confirmed | rejected | cancelled,
  createdAt, handledBy, handledAt, rejectReason }

# 出品 production
{ _id, storeId, dishId, qty, consumeItems: [{itemId, qty}], operatorId, createdAt }

# 剩余实点 stocktake
{ _id, storeId, itemId, actualQty, bookQty, diff, operatorId, createdAt }

# 库存余额 stock_balance
{ _id, storeId, itemId, qty, updatedAt }

# 门店 store（v0.8 新增 status / closedAt）
{ _id, code, name,
  status: "open" | "closed",   // 默认 open；闭店置 closed，复业置回 open
  closedAt,                    // 闭店时间；复业时清空
  createdAt }

# 用户 user（角色仅 2 类；管理端唯一预置、门店端 1 账号 = 1 门店）
{
  _id, openid, name, username,
  role: "manager" | "shop",   // 单值，不再多角色
  storeId,                    // shop 必填（1 门店）；manager 为 null（总仓）
  isActive: true, createdBy, createdAt
}
```

**字段说明**：
- `unit`：**自由输入文本**，不做固定枚举、不做单位换算（拍板）。
- `dish.consumeItems`：即原「配方」数据，内嵌菜品；每行 `qty` = 每份用量。
- `role`：**单值**，恒 `manager` 或 `shop`；不再有 `roles[]` 多值、`stores[]` 多门店。
- `store.status` / `store.closedAt`（**v0.8 新增**）：`status` 默认 `open`；闭店置 `closed` 并写 `closedAt`，复业置回 `open` 且清空 `closedAt`。
- `user`（管理端）：系统预置 **1 条**，`role='manager'`、`storeId=null`，不可新增 / 不可删除。
- `user`（门店端）：由门店端注册开店时在同一事务写入，`role='shop'`、`storeId=本店`。
- **已删除集合**：`supplier`（供应商）、`recipe`（独立配方）、`shipment`（发货单，v0.5 已废弃）。
